# Data Model

The gamification backend persists core state in Postgres. Migrations are applied during backend startup by [plugin.ts](https://github.com/BTH-Trafikverket/our-backstage/blob/main/plugins/gamification-backend/src/plugin.ts) through [database.ts](https://github.com/BTH-Trafikverket/our-backstage/blob/main/plugins/gamification-backend/src/database.ts).

## Constraints and Consistency

The database is part of the business logic. Keep Zod schemas, service behavior, OpenAPI, and migrations aligned when changing any field.

Important constraints:

- Quest and badge titles are unique.
- Quest and badge XP rewards are non-negative.
- Quest and badge `subject_type` is `user` or `team`.
- Quest target counts and badge criterion target counts must be positive.
- `quest_progress` is keyed by `(subject_ref, quest_id)`.
- `xp_awards` allows either a quest award or a badge award, never both.
- Quest XP awards are unique by `(subject_ref, quest_id, awarded_on_completion_count)`.
- Badge XP awards are unique by `(subject_ref, badge_id)`.
- Badge criteria must reference quests with the same subject type as the badge.
- Scheduled webhook runs are unique by `(webhook_id, trigger_event_name, period_key)`.
- Domain events are unique by `(event_name, source_table, source_id)`.

## Trigger-Owned State

The following state is maintained by database triggers:

- Quest XP awards are written when `quest_progress.completion_count` reaches a multiple of the quest `target_count`.
- Badge criterion completion is updated from quest progress.
- Earned badges are inserted when all badge criteria are complete.
- Badge XP awards are written when a badge is earned.
- `subject_xp_state` is refreshed whenever `xp_awards` changes.
- Domain events are enqueued when quest progress awards XP or badges are earned.
- `updated_at` columns are kept current by shared trigger functions.
